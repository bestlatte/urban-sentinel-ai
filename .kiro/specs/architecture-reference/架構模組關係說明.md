# 智慧交通指揮系統 — 架構模組關係說明

本文件搭配 `模組架構圖_整合版.md` 第四節的內嵌邏輯藍圖閱讀，用一個完整情境帶你把圖中的箭頭關係串成一個故事。新版資料實作圖（五 JSON + REST/WebSocket）另見 `diagrams/architecture-json-live.svg`。

> 關鍵心法：**箭頭方向 = 資料流動方向**。
> - 實線單箭頭（`-->`）：把東西送過去。
> - 雙箭頭（`<-->`）：來回問答 / 讀寫。

---

## 一、先看四大層在做什麼

- **🖥️ 前端 FE**：指揮官看的儀表板（圖表、彈窗、地圖、對話框）。所有畫面透過 `WebSocket Client` 接收後端主動推播，送出請求則走 Fetch REST；兩者都由同一個 FastAPI Server 提供。
- **⚙️ 後端 BE**：系統的大腦，內部又切成四個小工廠：
  - `資料驗證與正規化`（D1~D4）：把髒資料洗乾淨
  - `感知運算引擎`（P1~P5）：算指標、判事件級別
  - `路網推理與路徑規劃`（R1~R5）：算替代道路
  - `決策編排 Orchestrator`（A1~A4）：總指揮，`A2` 由 **LLM 決定要呼叫哪些工具**，但答案仍由決定性工具算
- **🤖 AI/LLM 層**：負責「動嘴」與「選工具」的部分，RAG 檢索 SOP、把判定結果寫成人看得懂的建議書與簡訊。
- **🗄️ 資料層 DB**：邏輯上是歷史車流、路網圖、事件記錄、SOP 向量庫、決策稽核與快取；競賽實作版對應為 `data/` 五個 JSON + Python 記憶體，只有 SOP 向量庫真的上雲（Bedrock KB / S3 Vectors）。

## 二、用一個情境走一遍：光復南路路面塌陷

以資料集中真實的第一筆事件為例（`data/live_incidents.json`）：

```
event_id        TPE_2026_ACC_001
type            Road_Collapse_Accident
location        光復南路與忠孝東路口南側
affected_segment RD_TPE_002
status/severity Closed / Critical
timestamp       2026-05-20 22:10
```

順著箭頭看它怎麼被處理。

### ① 平常就在跑的背景監測（還沒出事）

```
DB1(歷史車流/人流) --> D1(Loader) --> D2(校驗) --> D3(時間標準化) --> P1 & P2 & P3(感知三指標)
P1 & P2 & P3 --> P4(SOP規則引擎) --> P5(事件級別判定)
```

系統不斷讀時序資料，算出飽和度、人流成長率、漫遊比率。以 22:10 為例，`RD_TPE_002` 的 `Saturation_Score = 1.0`，`P5` 判為 **A 級**（門檻：≥0.95 為 A、0.85~0.95 為 B），於是發「預警觸發」經 `API → FWS` 以 WebSocket 主動推到前端，讓 `F2 異常自動彈窗` 跳出來。（對應命題模組 1：自動彈窗，不用人主動查。）

注意兩件事：

- 單位換算在 **D1~D3 正規化階段**完成，不在 P 系列：`Roaming_User_Pct` 原始是百分點（例如 `32.0`）須除以 100，`Growth_Rate` 已是小數率不可再轉換。`P3` 拿到的一律是 `0.0~1.0`。
- [2026-07-28 更正] 人流資料已由主辦方補齊真實 `signaling_crowd_density.csv`，`classification = provided`，`F1` 圖表**不再需要**標示 Simulated／Demo（原模擬版本 `Is_Simulated=true` 已棄用）。

### ② 事件注入進來

```
F3(事件注入面板) --> FWS --> API --> D4(事件注入監聽器) --> A1(事件分類器)
D4 <--> DB3(事件記錄庫)
```

指揮官在前端 `F3` 選取／匯入事故（送出走 REST `POST`，後續進度與結果由 WebSocket 推回）。`D4` 一邊把事件存進 `DB3`，一邊丟給 `A1` 分類。因為 `status=Closed`、`severity=Critical` 且 `affected_segment` 是 `RD_*`，命中 **SOP 第 2 條**（道路封閉與上游分流）。

### ③ 總指揮 A2 開始調度（這是全圖的樞紐）

`A2 Agent Orchestrator` 是整張圖箭頭最多的節點，因為它是總指揮。它本身是一顆 **LLM（Strands Agent + Bedrock）**，負責讀懂「這次事件需要什麼」並決定呼叫哪些工具；但它不自己算答案。它會做幾件事：

```
A1 --> A2                    （拿到事件分類）
P5 --> A2                    （拿到事件級別 A/B 級）
A2 <--> K3(RAG檢索) <--> DB4 （去 SOP 向量庫查「塌陷該怎麼辦」）
A2 --> R1(Graph Builder)     （叫路網組去算替代道路）
```

### ④ 路網推理鏈（R1~R5 是一條生產線）

```
R1(建圖) <--> DB2(路網圖) & DB6(Redis)
R1 --> R2(上下游判定) --> R3(候選路徑篩選) --> R4(主/次疏散路徑) --> R5(排除理由記錄) --> A4
```

這一整條就是命題模組 2 的核心：避開塌陷路段、算出主要與次要疏散路徑，還把「為什麼排除某條路」記下來（`R5`），之後要在前端解釋給評審看。

以本事件實際資料為例，`RD_TPE_002` 的替代清單是 `[004, 005, 006, 008]`，篩選結果：

| 候選 | 容量 | 飽和度 | 相交關係 | 結果 |
|---|---:|---:|---|---|
| `RD_TPE_004` | 2500 | 0.78 | 上游、直接相交 | **主要路線** |
| `RD_TPE_005` | 4000 | 0.65 | 下游、直接相交 | **次要路線** |
| `RD_TPE_006` | 3200 | — | 非直接相交 | 排除 |
| `RD_TPE_008` | 600 | — | 容量 <1000 且非直接相交 | 排除 |

排除條件是：事故封閉、容量低於 1000、非候選、非直接相交、僅下游、流向不符，**以及飽和度 ≥0.85**（命題要求避開飽和路段）。

但飽和有一個 SOP-2 例外，這是命題與 SOP 的折衷：

```
飽和度 ≥0.85 的候選
   ├─ 還有其他未飽和的合格候選 → 排除，記 saturated（預設）
   └─ 它是唯一合格候選         → 保留為主線，記 saturated_but_retained
                                  + 啟動長綠燈、綠燈延長 25%
```

理由：命題驗收要求「避開已達飽和狀態的路段」，但 SOP 第 2 條規定主要疏散路徑飽和時應維持並延長綠燈。預設排除可滿足命題，例外保留可避免「無路可走」而違背 SOP-2。本事件兩條候選（0.78、0.65）都未達 0.85，所以例外不會被觸發。

### ⑤ 同時算恢復時間，並記錄決策軌跡

```
A2 --> A3(ETE規則式計算) --> A4(Decision Trace Logger) --> DB5(稽核)
```

`A3` 依 SOP 第 7 條算 ETE，`A4` 把整個決策過程（含 A2 這次選了哪些工具）寫進 `DB5`，這就是模組 4「可解釋性」的資料來源。

本事件的 ETE 實算：

```
ETE = base_clearance + max(0, (平均飽和度 - 0.5) × 60)
    = 60 (Critical) + (1.0 - 0.5) × 60
    = 90 分鐘  →  預計恢復 2026-05-20 23:40
```

三筆事件的固定驗收值為 **ACC_001 = 90 分、EVT_002 = 70 分、EVT_003 = 41 分**。

### ⑥ 讓 LLM 把結果寫成文件

```
A2 --> C1(交控建議書) & C2(號誌配時) & C3(跨系統聯動)
A2 <--> LLM_A2  （把判定結果轉成人話解釋）
A2 -->|漫遊>=30%| C4(多語簡訊)
```

注意 `C4 多語簡訊` 那條有條件：由 `A2` 統一編排（跟 C1/C2/C3 同一個總指揮），只有當 `P3` 算出的**漫遊比率 ≥ 30%（即 `0.30`）** 時，`A2` 才會呼叫 `C4`（對應 SOP 第 6 條、命題模組 5）。為什麼閘門是 P3、觸發卻掛在 A2？因為簡訊內容要帶事故位置、類型、ETE、改道路線，這些只有 A2 編排時才拿得到；P3 只提供「漫遊比率」這個判斷數字。否則（未達門檻）只出中文訊息。

本事件在 22:00 的 as-of 人流中（依主辦方補齊之真實 `signaling_crowd_density.csv`，2026-07-28 更正），`BS_TPE_101` 為 `0.40`、`BS_XY_ATT` 為 `0.30`，因此 SOP 第 6 條成立，多語簡訊會被觸發（`BS_TPE_DOME` 真實漫遊率僅約 0.05~0.06，不構成觸發依據）。

這裡也要強調第二層原則：`C1~C4` 與 `LLM_A2` 都是 LLM，但它們只能**表達** A3／R 系列算出的數字與路線，不得改寫事件 ID、位置、級別、路線、ETE 或 SOP 條款編號。

### ⑦ 結果全部回傳前端

```
C1 & C2 & C3 & C4 --> API --> FWS --> F5(建議書/簡訊卡片) F4(地圖) F7(決策依據)
```

建議書、簡訊、路徑地圖、決策依據全部透過同一個 `API → FWS` 以 WebSocket 推回前端顯示（`POST` 也會同步回傳同一份結果，作為推播失效時的保底）。前端只顯示後端給的 `DecisionResult`，不在 JavaScript 重算規則、路線或 ETE。

### ⑧ 評審現場問 What-if（模組 3）

```
F6(對話視窗) --> API --> W2(對話狀態管理) <--> W1(What-if LLM)
W1 <--> K3(RAG) <--> DB4    （查 SOP 條款）
W1 <--> A2                  （必要時重跑判定）
W1 --> API --> F6
```

指揮官問「如果 BL17 人數增加到 40000 會怎樣？」，`W1` 會去 `K3` 檢索 SOP、請 `A2` 用假設參數重新呼叫 Python 工具重算，然後引用條款回答。

順序很重要：**LLM 解析參數 → Python 工具重算 → LLM 敘述**。不可以只把問題丟給 LLM 直接回答。SOP 第 3 條的門檻是 `Growth_Rate > 0.30` 或 `User_Count > 25000`；[2026-07-28 更正，依真實資料] 22:15 as-of 的 BL17 `User_Count = 31,000`（`Growth_Rate` 實為 `0.08`），已滿足 `User_Count > 25000` 這項門檻，所以就算不做假設也已成立。What-if 屬模擬，不寫入 `DB5`。

## 三、一句話記住整體

> **資料層**存東西 → **後端**洗資料、算指標、判級別、規劃路徑 → **AI 層**檢索 SOP 並寫成建議書/簡訊 → **前端**顯示，並支援互動問答。

而 `A2 Agent Orchestrator` 就是那個「站在中間、指揮所有人」的角色，所以它的箭頭最密。看圖時，只要先找到 `A2`，再看「誰餵資料給它、它又叫誰去做事」，關係就清楚了。
