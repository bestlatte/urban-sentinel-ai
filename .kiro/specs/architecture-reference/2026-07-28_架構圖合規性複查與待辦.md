## 二、尚未處理的問題（依風險排序）

### 2.1 【中風險】模組1「動態時序監測儀表板」目前不是真的「動態」——沒有背景週期性監測

**架構圖原文（`模組架構圖_整合版.md` 情境A、`架構模組關係說明.md` 同段落）**：

> 「系統不斷讀時序資料，算出飽和度、人流成長率、漫遊比率...於是發『預警觸發』經
> `API → FWS` 以 WebSocket 主動推到前端...**後端每 5~15 秒推進一次**並以 WebSocket
> **主動推播**；前端輪詢僅為斷線時的退路。」

**命題簡報原文（第4頁、第6頁）**：
> 「系統須具備『自動感知』能力——不只是對話機器人，而是能**隨時間推移自動偵測異常**...
> 數據達 SOP 預警門檻時，Dashboard 自動跳出分析摘要與預警提示，**無需人工查詢**。」

**實際程式碼現況**：
- 後端：`main.py` 的 `@app.on_event("startup")`（`_startup_rule_scan`，Phase 9.8）只在
  **伺服器啟動時執行一次** `evaluate_rules` + `handle_trigger_batch`，之後沒有任何背景排程
  再跑第二次。`grep -rn "setInterval|polling|poll" frontend/js/*.js main.py src/*.py` 完全
  沒有命中。
- 前端：`app.js` 的 `fetchDashboard()` 只在 `DOMContentLoaded` 時呼叫一次；`ws.js` 只有
  WebSocket 斷線 3 秒後重連連線本身的邏輯，沒有任何輪詢重新抓 `/api/dashboard` 的機制。

**後果**：F2「異常自動彈窗」目前只會在**有人手動透過 F3 注入事件、呼叫
`/api/incidents/evaluate`** 之後才跳出來。系統不會在沒有人操作的情況下，自己持續監測、
自己發現數據已經跨過 SOP 門檻並主動示警——這正是命題投影片點名的「自動感知」核心賣點，
不是模組2（事件處置）能替代的行為。

**由來**：`KIRO_BUILD_CHECKLIST.md` 第9.8項是總架構師（我）當時的簡化決定：
「demo資料時間跨度短，先求『啟動時跑一次』能動即可，不強求真的定時輪詢」——這個決定
當下沒有回頭對照這三份原始架構圖裡「每 5~15 秒」的明文要求，判斷有誤。

**建議修法（尚未實作，供評估）**：
- `main.py` 用 `asyncio.create_task` 起一個背景迴圈（`asyncio.sleep(5~15)`），每輪重跑
  `GATEWAY.evaluate_rules()`，跟上一輪結果比對找出等級轉換（`normal→B`、`B→A` 或反向），
  有變化才呼叫 `handle_trigger_batch()` 並廣播 `decision.alert.v1` / `dashboard.updated.v1`。
- **注意**：目前資料是固定歷史資料（不會隨真實時間新增新數值），這個迴圈重跑的結果理論上
  每次都一樣，「自動偵測異常」在 demo 上比較像是「系統持續在跑」的行為證明，不是真的會抓到
  新變化——但至少讓 Dashboard 符合命題要求的運作模式，評審看得到系統有在自己跳動。
- 如果團隊評估「demo 全程都會有人操作、評審不會盯著看背景是否自己跑」，也可以決定不修、
  只在簡報時口頭說明「демo 資料集是固定快照，背景監測迴圈的價值在正式環境才會顯現」——
  這是可以接受的取捨，但要是團隊自己知情決定，不是遺漏。

**狀態**：🚧 已鷹架，等 Kiro 實作。`main.py` 新增了 `_periodic_rule_monitor()`（完整演算法寫在
docstring 裡）+ `_start_periodic_rule_monitor()`（負責排程，目前 `pass`，故意不擋住伺服器
啟動）。已用 `uvicorn` 實測確認鷹架狀態下伺服器仍能正常啟動、`pytest tests/ -q` 102 passed
無回歸。對應 `KIRO_BUILD_CHECKLIST.md` Phase 12.1（重新排序後：架構複查修正移到 Phase 11 之後、加分項之前，見該檔案 Phase 12 開頭說明）。

### 2.2 【中風險】`chat.loading_start.v1` / `chat.loading_step.v1` 兩端都接好、中間斷線（死代碼）

**架構圖依據**：`04-system-architecture.md` §5 WebSocket 總表明列這兩個事件，用途是 F6
對話面板顯示「AI 思考中」進度動畫。

**實際程式碼現況**：
- `src/agent/loading.py` 有完整實作 `broadcast_loading_start()` / `broadcast_loading_complete()`。
- `frontend/js/ws.js` 也有對應的 `case "chat.loading_start.v1"` / `"chat.loading_step.v1"`
  處理分支。
- 但 `main.py` 的 `POST /api/what-if` 呼叫 `orchestrator.handle_user_query()` 時完全沒有
  傳入 `ws_broadcaster`；`handle_user_query()` 函式簽章本身也沒有這個參數可以往下傳給
  `process_whatif_request()`。整條推播路徑「頭尾都接好、中段斷開」，**在真實請求流程中永遠
  不會觸發**。

**後果**：如果 demo 現場 Bedrock LLM 呼叫有延遲（AWS 網路狀況、Strands Agent 真的連線），
使用者送出 What-if 問題後畫面會「看起來卡住」直到 REST 回應才有反應，沒有任何進度提示。

**修法**：`main.py` 的 `what_if()` 把 `ws_manager.broadcast` 傳進
`orchestrator.handle_user_query(..., ws_broadcaster=ws_manager.broadcast)`；
`handle_user_query()` 簽章加一個可選參數 `ws_broadcaster=None`，轉傳給
`process_whatif_request()`（該函式本身已經有 `ws_broadcaster` 參數，只是沒人傳）。

**狀態**：✅ 已修正。改動範圍確實很小（兩處各加一個參數/一行傳遞），總架構師直接動手修，
不需要走鷹架流程。`src/agent/loading.py` 的 `broadcast_loading_start_sync`/`_complete_sync`
本來就已經正確處理「在運行中的 event loop 裡呼叫」這個情境（用 `asyncio.ensure_future`
而非 `run_until_complete`），接上後不需要額外修正。已跑過 `pytest tests/ -q`（102 passed）
確認無回歸。對應 `KIRO_BUILD_CHECKLIST.md` Phase 12.2（此項已標記免做，供 Kiro 跳過）。

### 2.5 【高風險，新發現，2026-07-28】A2 Orchestrator 不是真的 Strands Agent；C1-C4 從未真的呼叫 Bedrock

**依據**：AWS 部署分層圖「應用層」區塊，明確畫出 `Agent編排(=A2 Orchestrator)` 這個框，
框內是 `Strands Agents SDK：LLM決定要call哪個工具`，往下三條 `call` 箭頭指向
`路網規劃R1-R5`／`ETE計算A3`／`SOP規則判定P4`；再往下一格是 `生成建議書/簡訊C1-C4：
呼叫Bedrock FM`。這四個節點都標🔴核心必做。

**實際程式碼現況**：
- `src/orchestrator.py::handle_incident()`（也就是 A2 的核心邏輯）是**純粹的決定性 Python
  流程**：`grep -n "strands|Strands|Agent(" src/orchestrator.py` 只在註解裡出現，沒有任何
  一行真的 import/建立 Strands Agent。要不要呼叫 `plan_routes`（路網規劃）是靠
  `classify_incident()`（查表函式，不是LLM）算出的布林值 `requires_rerouting` 決定；
  `calculate_ete`／報告生成則是無條件都會呼叫。整個「選工具」完全是寫死的 if/else，
  不是 LLM 決定的。
- 真正符合圖上畫法（Strands Agent、LLM 自己決定要呼叫哪個工具）的，只有 **W1**
  （`src/agent/whatif_agent.py`）——但 W1 服務的是 What-if 對話功能，不是主線的事件
  處理流程（A2）。
- `src/reporting.py::_generate_with_llm()` / `_generate_notification_with_llm()` 目前
  都是直接呼叫保底模板函式（`_generate_c1_c3_fallback`／`_generate_c4_fallback`），
  從 Phase 7 就是已知 TODO（「等 Phase 7 Agent 全部完成後才接真正的 LLM 呼叫」），
  從沒有實際執行過真正打到 Bedrock FM 的那條路徑。

**張力（要老實面對，不能假裝不存在）**：這個專案從一開始就建立在「golden value 精確值
斷言」的測試哲學上（ETE 必須逐字是 90/70/41 分鐘，不是「差不多」），如果讓 LLM 真的自由
決定「這次要不要呼叫 ETE 計算」，理論上會讓黃金驗收值變得不穩定——這正是本專案一路以來
刻意把「算答案」限定在決定性 Python 的原因。**如果只是為了符合這張圖就讓 LLM 完全自由
決定要不要呼叫這些工具，會直接跟專案的核心測試哲學衝突**，不能不假思索地照做。

**採用的調和方案**（使用者已明確指示「上面有寫就是要做」，故直接排入開發清單，非僅記錄）：
1. 新增 `src/agent/a2_tools.py`：把 `plan_routes`／`calculate_ete`／`evaluate_rules`
   （皆透過 `orchestrator.GATEWAY`）包成 `@tool` 函式，讓 A2 可以真的被 Strands Agent 呼叫——
