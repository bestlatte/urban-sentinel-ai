## 一、元件定位

W2 是模組三的「對話記憶體」。它負責管理使用者與系統之間的多輪對話狀態，讓 W1 在每次收到新問題時，能知道前面聊過什麼、使用者累積了哪些假設。

W2 **不做推理、不查 SOP、不呼叫任何工具**。它只做三件事：記住、整理、交出去。

---

## 二、功能需求

### REQ-1：維護多輪對話歷史

- 記錄每一輪的使用者輸入與系統回覆（含時間戳）。
- 保留最近 10 輪對話。超過 10 輪時，丟棄最早的那輪。
- 每一輪至少包含：使用者原始訊息、W1 的回覆摘要或完整回覆。

### REQ-2：累積假設參數

- 當 W1 從使用者訊息中解析出假設參數（例如「BL17 人數 = 40000」），W2 應記錄這些假設。
- 後續對話中，W2 將已累積的假設參數一併交給 W1，讓 W1 能理解「在前面的假設基礎上，再加上新的假設」。
- 假設參數的「解析」是 W1 做的，W2 只負責「存」和「帶上」。

### REQ-3：組合上下文交給 W1

- 每次新訊息進來時，W2 將以下資訊打包交給 W1：
  - 使用者本次的新訊息
  - 最近 N 輪的對話歷史（N ≤ 10）
  - 目前累積的假設參數清單
- W1 拿到這個打包後的上下文，才開始做意圖判斷與工具呼叫。

### REQ-4：Session 生命週期

- **建立**：使用者首次發送訊息時，自動建立一個 session。
- **清除條件**（任一即觸發）：
  - 前端頁面關閉或重新整理（WebSocket 斷線時後端偵測並清除）
  - 使用者點擊「清除對話」按鈕（前端發送清除請求）
- **不做超時機制**（Demo 場景不需要）。

### REQ-5：Session 隔離

- 若多個使用者同時連線（Demo 通常不會，但保險起見），不同 session 之間的對話歷史互不干擾。
- 使用 session ID 區分（可綁定 WebSocket connection ID）。

---

## 三、儲存方式

- 純後端 Python 記憶體（dict / list）。
- 不做持久化、不寫資料庫、不寫檔案。
- Server 重啟 = 所有 session 清空（Demo 可接受）。

---

## 四、不屬於 W2 的事（明確排除）

- ❌ 判斷使用者意圖（那是 W1 的工作）
- ❌ 呼叫 K3 查 SOP（那是 W1 的工作）
- ❌ 呼叫 A2 重算（那是 W1 的工作）
- ❌ 解析假設參數（W1 解析後告訴 W2 存起來）
- ❌ 生成回覆文字（那是 W1 的工作）
- ❌ 定義前端 UI 行為（那是 F6 的工作）

---

## 五、與其他元件的關係

```
F6（前端）
   │ 使用者訊息
   ▼
API Gateway
   │ 路由到 W2
   ▼
W2：記錄本次訊息 → 組合上下文（歷史 + 假設參數 + 新訊息）
   │ 打包好的上下文
   ▼
W1：判斷意圖 → 呼叫工具 → 生成回覆
   │ 回覆結果
   ▼
W2：記錄本輪回覆 + 更新假設參數（如果 W1 有新假設）
   │
   ▼
API → F6 顯示
```

---

## 六、成功標準

1. 使用者連續問 3 題相關問題（例如逐步加假設），W1 能正確理解上下文指代關係（「那」「同時」「剛才」）——前提是 W2 有正確帶入歷史。
2. 點擊「清除對話」後，下一次提問 W1 不會再參考之前的對話。
3. 超過 10 輪時，最早的歷史被丟棄，但不影響最近的對話理解。
4. 兩個不同 session 之間的對話不會互相污染。

- Session ID 的生成方式（留待與 API Gateway 整合時定義）
