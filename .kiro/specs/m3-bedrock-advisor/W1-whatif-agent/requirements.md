## 一、元件定位

W1 是模組三的「大腦」。它是一個 LLM Agent，收到 W2 整理好的上下文後，判斷使用者意圖，決定是否需要呼叫工具（K3、A2），最後組合出結構化 + 自然語言的回覆。

W1 的核心原則：**可以選工具、可以寫文字，但不可以自己編造 SOP 條款、數字、路線或 ETE。**

---

## 二、功能需求

### REQ-1：意圖分類

W1 收到上下文後，第一步是判斷使用者意圖，分為三類：

| 意圖類別 | 判斷依據 | 後續動作 |
|---------|---------|---------|
| **閒聊/打招呼** | 非交通相關、禮貌用語、感謝 | 直接 LLM 回覆 + 引導使用者提出交通問題，不呼叫任何工具 |
| **SOP 知識查詢** | 詢問 SOP 規則內容、門檻、公式 | 呼叫 K3 檢索 → 引用條款原文回答 |
| **What-if 模擬** | 包含假設條件（「如果…」「假設…」「萬一…」） | 呼叫 K3 + 呼叫 A2 用假設參數重算 → 組合完整回答 |

### REQ-2：What-if 模擬的回覆內容

當判定為 What-if 模擬時，W1 的回覆應包含以下結構化資訊：

1. **觸發條款**：列出被觸發的 SOP 條款（section_number + title）
2. **判定依據**：說明為什麼觸發（引用門檻數值 vs 假設值的比較）
3. **預期動作**：SOP 規定的處置步驟
4. **路網影響**：如果有路線變動，列出主/次疏散路徑與排除路段
5. **ETE**：如果相關，列出預計恢復時間與計算過程
6. **延伸問題**：提供 3 個相關的後續問題建議，啟發使用者繼續探索

延伸問題應基於當前回答的上下文生成，例如：
- 如果剛回答了第 3 條觸發，延伸問題可能是「如果同時散場機制也啟動呢？」
- 如果剛算了 ETE，延伸問題可能是「如果延長綠燈 30% 能改善多少？」

### REQ-3：SOP 知識查詢的回覆內容

當判定為 SOP 知識查詢時，回覆應包含：

1. **引用的 SOP 條款原文**（來自 K3，不改寫）
2. **白話解釋**（用自然語言解釋條款意思）
3. **延伸問題**：提供 2~3 個相關的後續問題

### REQ-4：回覆格式（雙格式輸出）

W1 的每次回覆同時提供兩種格式：

- **結構化 JSON**：包含固定欄位（`intent_type`、`triggered_sops[]`、`actions[]`、`ete`、`route_impact`、`suggested_questions[]`、`current_data_snapshot` 等），供 F6 渲染 Decision Card、SOP Badge、ETE Badge。
- **自然語言摘要**：一段人話風格的回覆，供 F6 的對話氣泡使用。

兩者內容一致，只是呈現方式不同。前端可自行決定要用哪種或兩者並用。

### REQ-5：引用當前路況數據

回答 What-if 時，除了引用 SOP 條款，也應帶出當前的即時數據（來自 A2 重算時的 snapshot），讓回答具有時效性。例如：

- 「目前 BL17 已有 31,000 人（[2026-07-28更正] 真實 Growth_Rate 約 0.08，觸發依據為 User_Count > 25,000 門檻而非成長率），若依您的假設增至 40,000…」
- 「目前忠孝東路飽和度 0.99（A 級），若再加上光復南路塌陷…」

### REQ-6：精準引用，不得編造

- SOP 條款編號、標題、原文內容：必須來自 K3 的回傳，不得自行編造。
- 路線、ETE、事件級別：必須來自 A2 的重算結果，不得由 LLM 自己推算。
- 若 K3 回傳「無相關條款」，W1 應明確告知使用者「SOP 未涵蓋此情境」。

### REQ-7：邊界問題處理

| 情境 | W1 的處理方式 |
|------|-------------|
| 完全不相關（「台灣總統是誰」） | 禮貌拒絕：「我是交通策略諮詢顧問，目前只能回答交通應變相關的問題。請問有什麼交通方面想了解的嗎？」 |
| 交通相關但 SOP 未涵蓋（「如果下暴雨怎麼辦」） | 說明 SOP 邊界：「目前 SOP 未針對此情境有明文規定。但依現有規則推測…」，並明確標示推測部分非 SOP 明文。 |

### REQ-8：A2 尚未整合時的退化模式

- 設計上 W1 呼叫 A2 進行假設參數重算。
- 若 A2 尚未完成或不可用，W1 應退化為「僅用 K3 檢索 + LLM 推理」模式：
  - 仍呼叫 K3 取得 SOP 條款
  - 用 LLM 根據條款內容推理（標示為「基於條款推估」而非精確計算）
  - 不提供精確的路線計算或 ETE 數值
- 退化模式讓模組三不被 A2 的開發進度阻擋。

## 三、工具清單（W1 可呼叫的工具）

| 工具 | 對應元件 | 何時呼叫 |
|------|---------|---------|
| `query_sop(question)` | K3 | 需要查 SOP 條款時 |
| `simulate_scenario(assumptions)` | A2 | 需要用假設參數重算路線/ETE 時 |

W1 透過 Strands Agent 的 `@tool` 機制呼叫這些工具。工具的具體 function signature 留待 design 階段定義。

## 四、不屬於 W1 的事（明確排除）

- ❌ 管理對話歷史（那是 W2 的工作）
- ❌ 自己計算路線或 ETE（那是 A2 → R1~R5 / A3 的工作）
- ❌ 自己建 SOP 向量索引（那是 K3 / DB4 的工作）
- ❌ 決定前端怎麼渲染回覆（那是 F6 的工作）
- ❌ 正式決策留痕（What-if 模擬不寫 DB5）

## 五、與其他元件的完整互動流程

```
W2 交給 W1：
  {
    new_message: "如果 BL17 人數到 40000 會怎樣？",
    history: [...最近 10 輪對話...],
    accumulated_assumptions: [...]
  }

W1 內部流程：
  1. 意圖分類 → What-if 模擬
  2. 呼叫 K3("BL17 人數超過門檻觸發什麼") → 回傳 SOP §3
  3. 呼叫 A2(assumptions: {BS_MRT_BL17.User_Count: 40000}) → 回傳計算結果
  4. 組合回答：
     - 結構化 JSON（觸發條款、動作、路網影響、ETE、延伸問題）
     - 自然語言摘要

W1 回傳給 API → F6 顯示
W1 同時告訴 W2：「這輪的假設參數是 BL17=40000，請記住」
```

## 六、成功標準

1. 給定閒聊輸入（「你好」），W1 不呼叫 K3 或 A2，直接回覆引導語。
2. 給定 SOP 查詢（「ETE 怎麼算」），W1 呼叫 K3 並回傳包含 SOP 第 7 條原文的回答。
3. 給定 What-if 問題（「如果 BL17 到 40000」），W1 呼叫 K3 + A2，回傳包含觸發條款 + 預期動作 + ETE 的結構化回覆。
4. 回覆中的 SOP 條款內容與 `emergency_traffic_sop.json` 原文完全一致。
5. 回覆中的 ETE / 路線 / 級別數值與 A2 回傳的計算結果一致（不被 LLM 改寫）。
6. 每次 What-if 回覆都附帶 3 個合理的延伸問題。
7. A2 不可用時，系統仍能回覆（退化模式），且明確標示為推估。
